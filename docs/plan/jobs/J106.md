# J106 · The design lab: a side space for exploring the look

**Chapter:** the tools
**Serves:** N1 N5
**From the user:** request `2026-10-26 #12`, `#13` (one theme only) (docs/records/requests/)
**Verdict:** doable now — files only, in their own folder; nothing the game, the site or the current job loads

## Goal
A place on the side, `design/`, where Claude works out bolder ideas for how
Bar3D's screens could look and feel, and shows them to the user as pictures
they can open on the phone and react to ("I like this one", "more of that").
Nothing in it is used by the bar until the user says "use it"; then the
chosen idea becomes its own job, built with the UI Editor's themes and
screens like any other change.

## Scope
- `design/`: its README (what the lab is, how a round works), a log of what
  the user liked and didn't, and one look-book per round.
- The look-book is a page shown privately to the user (a claude.ai page,
  not on joshuavelasco.com).
**Not in scope:** the bar's menus (`bar/web/`), the UI system (`ui/`, the
themes, the UI Editor), the site, the deploys. No new font, library or
picture from outside: only what the repo already has a licence for
(`ui/fonts/`, `ui/CREDITS.md`).

## Research
- **What exists today.** The shared look is `ui/`: 12 themes
  (`ui/system/themes/`, Ember is the bar's), 22 controls built from tokens
  (`ui/system/tokens.json`, `ui/looped.css`), sample screens
  (`ui/system/screens/`, among them `bar-menu.json`: the Jukebox over the 3D
  view). The bar's real menus are `bar/web/menu.js` (Handbook:
  `docs/handbook/ui/menus.md`). Themes already change colour, glass, shape
  and type; what they don't change is *layout and behaviour*: where the menu
  lives, how it opens, how much of the bar it hides. That's where the lab
  looks first.
- **Fonts** usable without asking: Archivo, Martian Mono, Limelight,
  Unbounded, Righteous (all OFL, already in `ui/fonts/`).
- **Deploys.** A top-level `design/` would count as "the game changed" in
  `deploy.yml`'s filter and start a game deploy once it reaches `main`. So
  the lab stays on this job's branch (`job/J106`) until the user wants it on
  `main`; then `design/` is added to that filter in the same ship.
- **How studios do it:** a "look-book" or mood board: a few clearly
  different directions side by side, the same content in each so only the
  style changes, pick one, then refine it in rounds.

## Pieces
- **J106.1** The lab set up: `design/README.md`, `design/likes.md`, and the
  first look-book (round 1: six directions for the in-bar menu, same
  Jukebox content in each). *Check:* open the look-book link from the chat
  on the phone; six phone-shaped pictures, each with a name and a line.
- **J106.2** One theme only (request 2026-10-26 #13): the page shows Coaster alone, on two screens, with its colours, lettering and controls. *Check:* open the same link; one theme, Coaster.
- Later changes are added as pieces when the user reacts.

## Done when
The user has picked a direction and says "use it": that becomes a new job
(a theme and screens in the UI Editor, the bar's menus). Until then the job
stays open on its branch and touches nothing live.

## Risks
- The lab drifts from what the engine can draw: every direction names what
  it would need (a theme only, new controls, or engine work).
- Shipping `design/` to `main` without the filter change would start an
  unneeded game deploy (GitHub minutes, KI-44): the filter change ships with it.
