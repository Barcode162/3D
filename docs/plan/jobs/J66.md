# J66 · Deploys never wait for, or get stopped by, the tests

**Chapter:** the tools
**Serves:** N5 (judged on the phone: a build reaches it in minutes)
**From the user:** the approved order (request 2026-10-24 #7); known issues KI-32 and KI-33
**Verdict:** doable now — our own workflow and test; no cost

## Goal
A new build is on your phone about 6 minutes after it's pushed, every time:
it never waits behind the previous build's hour of tests, and a test that
trips on a slow machine's timing never keeps a build from going live.

## Where it stands
- `deploy.yml` runs one deploy at a time (concurrency group `pages`, never
  cancelled), and the tests are steps of the same job, so each deploy holds
  its turn through about an hour of tests. Run 215 (`666d414`) waited 47
  minutes behind run 214 (KI-32).
- The room test runs before the deploy (the room goes live with the build).
  Its "then it leaves after the grace period" check failed once (run 214):
  the watching player is closed as away after 9 s (the test's `AFK_MS`), and
  on a slow machine that came before the other player's leave reached it, so
  the leave was never seen and `31cb32d` didn't go live (KI-33).

## Scope
`.github/workflows/deploy.yml`, `tools/ci_status.mjs`, `tools/room_test.mjs`,
`tools/workflows_test.mjs`, their Handbook pages. **Not in scope:** the
browser tests' own failures on GitHub (KI-5, J54), the room's code.

## Design
- **J66.1** The deploy job keeps the build, the quick checks, the room's
  tests, the uploads and gh-pages, with its own turn (`pages`). The game's
  tests move to a second job, `tests`, that starts when the deploy job has
  succeeded and builds again on its own machine (the caches make that a few
  minutes), in its own queue (`game-tests`), so the next deploy only waits
  for the previous deploy (minutes), never its tests. Every setup step gets a
  time limit. The deploy reports keep working: the deploy job reports
  started and live (and its end, if it fails); the tests job reports the end;
  an end report for a build that is no longer the live one is not sent (a
  slow old test run never overwrites the newer build's row in Dev).
  Options not taken: cancelling an older build's tests when a newer one comes
  (its end report would land after the newer build's); uploading the built
  files between the jobs (large; the caches make a rebuild cheap).
- **J66.2** The room test's watcher stays active for longer than the leave
  can take (the test's `AFK_MS` 9 s → 20 s), so the check waits for the
  event rather than racing the away timer; the AFK check itself is unchanged
  (it waits `AFK_MS` + 6 s and still checks the 4004 "away").

## Pieces
- **J66.1** The tests in their own job after the deploy *Check:* the next
  push: Dev's game row says live about 6 minutes after the push even while the
  previous build's tests run
- **J66.2** The room test's grace check made steady *Check:* GitHub's room
  test passes on the next deploy (Dev's game row: no "room")

## Done when
`tools/workflows_test.mjs` passes (each test still runs after any failure,
within its time limit, and is reported); the room test passes here; on
GitHub the next deploy goes live while the one before is still testing.

## Risks
- A mistake in the workflow stops deploys: the workflows test checks its
  shape, and the ship's live check (Dev's rows) shows it within minutes; a
  revert is one job.
- The second build could differ from the deployed one: same commit, same
  steps, same caches.
