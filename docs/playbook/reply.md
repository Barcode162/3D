# Replying to the user

**When:** every reply.

The user reads on an iPhone, is new to graphics and code, and never needs to
know a file, a tool or a command. So: plain words (the glossary's), short, the
important thing first, no file names or commands unless asked. Say what to look
at on the phone, never "it should work".

## The four kinds of reply

**Understood** (after intake, before work):
> Got it: <what you understood, one line>. <Verdict, one line: doable now /
> after X / costs Y: your call / needs a try first / not possible because …,
> closest is … / against your rule "…">. <What happens next.>

**Done** (after a job or piece is live and checked):
> Build `<sha>`.
> - **J<n>.<k>** <where to stand or look> → <what you should see>. *If not, say:
>   broke J<n>.<k>*
> - …
> <Anything still running, and when it'll be known.> <Errors this session: none,
> or what went wrong and what changed so it can't happen again.>

**A question** (only when the decision is the user's: Charter §5):
> <The decision, one line.> I recommend **<option>** because <reason>.
> Other choice: <option> (<what it means>).

Exactly one question per decision, recommendation first; never a menu of
options without a recommendation.

**Something went wrong:**
> <What broke, one line.> <What it affects (or "nothing live").> <What I did.>
> <What changed so it can't happen the same way again.>

## Never

- Say something is done, live or fixed without having checked it.
- Hide an error, a red run or something skipped.
- Make the user choose between technical options; translate them into what
  the user will see, and recommend one.
